# 第四次实验LLM 语义压缩实验

## 1. 实验目的

在已有的 Agent History 管理基础上，引入 LLM 对较早的历史消息进行语义压缩，以减少后续请求需要携带的上下文 Token。

本轮实验只关注：

- LLM 语义压缩是否可行
- Summary 如何与原始 History 配合
- 多次压缩时如何避免 Summary 无限膨胀
- 当前压缩策略存在的问题

------

## 2. 基本思路

当 History 超过一定长度后，将较早的消息交给另一个 LLM 请求进行总结。

基本流程：

```text
History
   │
   ├── Recent History
   │      └── 保留原始消息
   │
   └── Old History
          │
          ▼
      Summary LLM
          │
          ▼
      History Summary
```

最终提供给 Agent LLM 的 Context：

```text
System Prompt
+
History Summary
+
Recent History
+
Current User Input
```

------

## 3. Summary 的增量更新

第一次压缩时：

```text
Old Summary = 空
New History = 较早历史
```

得到：

```text
New Summary
```

后续再次压缩时，不能简单地：

```text
Old Summary
+
New History
```

直接拼接。

否则会导致 Summary 本身不断增长。

正确方式是：

```text
Old Summary
       +
New History
       │
       ▼
   Summary LLM
       │
       ▼
New Summary
```

即：

```python
new_summary = summarizer(
    old_summary,
    new_history
)

self.summary = new_summary
```

每次压缩后使用新的 Summary 替换旧 Summary。

------

## 4. Summary 的压缩要求

Summary LLM 的主要要求：

1. 保留重要事实。
2. 保留用户明确提供的重要信息。
3. 保留正在进行的任务。
4. 保留重要决策。
5. 保留必要的工具调用及结果。
6. 删除无意义的闲聊。
7. 不虚构信息。
8. 避免重复内容。
9. 不描述摘要过程本身。
10. 直接输出新的 Summary。

目标不是复述完整聊天记录，而是：

> 尽可能使用更少的 Token 保留后续 Agent 仍然需要的信息。

------

## 5. 当前 ContextManager

当前 ContextManager 维护两个主要部分：

```python
self.summary
self.history
```

获取 Context 时：

```python
messages = []

if self.summary:
    messages.append(
        HumanMessage(
            content=f"[历史摘要]\n{self.summary}"
        )
    )

messages.extend(self.history)
```

因此：

```text
Summary
   +
Recent History
```

构成当前历史 Context。

------

## 6. 当前压缩触发方式

目前采用简单的 Token 阈值：

```python
def should_compress(self):
    return (
        len(self.history) > self.keep_recent
        and self._count_tokens(self.history) > self.max_tokens
    )
```

超过阈值后：

```python
ctx.compress()
```

压缩较早的 History，只保留最近的一部分消息。

------

## 7. 实验中发现的问题

### 7.1 每次达到阈值就压缩

当前策略类似：

```text
超过阈值
    ↓
立即压缩
```

如果阈值设置得比较低，就可能出现：

```text
对话
 ↓
达到阈值
 ↓
调用 Summary LLM
 ↓
继续对话
 ↓
再次达到阈值
 ↓
再次调用 Summary LLM
```

这会产生大量额外的 LLM 请求。

------

### 7.2 压缩本身也需要 Token

这是本轮实验中比较重要的问题。

假设：

```text
History = 10K tokens
```

进行一次 Summary：

```text
Summary Input  ≈ 8K
Summary Output ≈ 1K
```

那么仅仅为了完成压缩，就产生了约：

```text
9K tokens
```

的额外 LLM 调用。

因此：

> 压缩并不是免费的。

如果压缩之后只进行很少几次对话，压缩产生的成本甚至可能超过它节省的 Context Token。

------

## 8. 压缩收益具有摊销性质

假设：

```text
压缩前 Context = 10K
压缩后 Context = 3K
```

那么每一次未来请求大约节省：

```text
10K - 3K = 7K tokens
```

假设压缩本身消耗：

```text
8K tokens
```

那么需要经过多次后续请求，压缩成本才能被摊平。

可以粗略表示为：

```text
Break-even Calls
≈
Compression Cost
/
Saved Tokens Per Call
```

例如：

```text
8K / 7K ≈ 1.14
```

意味着后续请求次数越多，之前的压缩成本越容易被摊薄。

------

## 9. 当前阶段的结论

本轮实验验证了：

### LLM 语义压缩是可行的

可以通过：

```text
Old Summary
+
Old History
       ↓
    LLM
       ↓
New Summary
```

持续维护一份语义摘要。

### 但不能简单地“超过阈值就压缩”

因为：

```text
Compression
    ↓
本身就是一次 LLM 调用
    ↓
本身产生 Token 成本
```

因此后续需要从：

```text
“什么时候超过阈值”
```

进一步研究：

```text
“什么时候压缩才值得”
```

------

## 10. 下一步

下一轮重点研究：

### Cost-aware Context Compression

记录每次压缩：

```text
压缩前 History Token
Summary 输入 Token
Summary 输出 Token
压缩后 Context Token
```

进一步计算：

```text
Compression Cost
Saved Per Future Call
Break-even Calls
```

并尝试：

```text
Soft Limit
Hard Limit
Target Context Size
```

让 ContextManager 不再每次刚超过阈值就立即压缩，而是根据 Context 增长和压缩成本进行更合理的批量压缩。

AI： 您这个观察是很有道理的，我们来掰开看一下这个成本账。

**问题的核心：压缩本身是一次额外的模型调用**

如果每轮对话都先做一次"压缩"调用、再做一次"真正回答"的调用，那么单轮成本大致是：

- 原来：1 次调用，输入 = 当前完整上下文，输出 = 回答
- 现在：1 次压缩调用（输入 = 完整上下文，输出 = 摘要）+ 1 次回答调用（输入 = 摘要，输出 = 回答）

也就是说，**输入被读了两遍**。第一遍读全文去生成摘要，第二遍读摘要去回答。在上下文还比较短的时候，摘要调用省下的那点输入，几乎肯定抵不过多读一遍全文的开销，所以净成本是上升的——这正是您说的"压缩调用的 token 数比节省的多"。

**什么情况下压缩才划算**

关键在于"上下文增长速度"和"压缩触发频率"的关系：

- 上下文越长、累积越多，压缩带来的收益才越明显；
- 如果每轮都压缩，等于每轮都额外付一次"读全文"的钱，短对话里这就是纯亏。

**通常更合理的做法**

1. **按阈值触发**，而不是每轮都压。比如上下文超过某个长度（或超过模型窗口的某个比例）时才压缩一次。
2. **压缩比拉大**：只有当"全文 token 数 ÷ 摘要 token 数"足够大时，压缩才开始回本。可以设一个门槛，比如压缩比低于 2~3 倍就干脆不压。
3. **分段/滑窗**：保留最近若干轮原文，只对更早的历史做摘要，避免每次都重读一遍全部内容。
4. **缓存**：如果压缩调用和回答调用的前缀相同，可以利用 prompt caching 降低重复读取的成本。

**一句话总结**

"每轮都压缩"在成本上大概率是负收益；压缩应该是一个**按需触发的、有明显压缩比才启用**的优化手段，而不是默认动作。判断标准很简单：`压缩调用多花的 token` 是否小于 `后续每次回答因上下文变短而省下的 token × 后续调用次数`。只有后者更大时，压缩才真正省钱。

- 当 `L → ∞`，这个摊销 ≈ `a`，也就是"几乎不再额外付压缩的钱"。

1. 压缩调用次数下降，摊销的额外成本趋近于 `a`；

- 极端情况：`maxlen` 大到接近模型窗口甚至不触发，就退化成"根本不压缩"，此时回到单调用基线。

**粗略成本模型**

设每轮新增 `a` 个 token，阈值 `L`，压缩后摘要长度 `s`（压缩比 `L/s`）。

- 每积累约 `L - s` 的新 token 触发一次压缩，即每约 `(L - s)/a` 轮压一次。
- 单次压缩开销 ≈ `L`（读全文）+ `s`（写摘要）。
- 摊到每一轮的压缩成本 ≈ `(L + s)·a / (L - s)`。

观察这个式子：

- 当 `L` 很小，分母 `L - s` 很小，摊销成本暴涨——这就是"每轮都压、越压越亏"的情况。
- 当 `L → ∞`，这个摊销 ≈ `a`，也就是"几乎不再额外付压缩的钱"。

**所以调大 `L` 的收益**：

1. 压缩调用次数下降，摊销的额外成本趋近于 `a`；
2. 减少有损压缩的次数，摘要信息损失和误差累积更少；
3. 减少"压缩边界抖动"，上下文更连续。

**但代价在另一边**：

每次回答要读的上下文，平均约 `(s + L)/2`，最大到 `L`。所以 `L` 越大，**每次回答的输入越长、越贵、延迟越高**，还容易踩到"中间信息被忽略"的长上下文性能衰减。

**结论：存在一个最优阈值**

总每轮成本 ≈ `回答输入(随 L 近线性上升) + 压缩摊销(随 L 下降趋近 a)`。前者是增函数，后者是减函数，两者相交处附近就是最优点。所以：

- `L` 太小 → 双调用太频繁，纯亏（你上一条说的问题）；
- `L` 太大 → 几乎不压缩，等于放弃压缩的收益，还白付长上下文；
- 中间某个 `L` → 摊销降下来了、回答输入还没涨太多，这时候调大阈值才真正"有用处"。

**实操上的建议**

1. 阈值不要设成"每轮触发"，也别设到窗口上限，取窗口的某个比例（比如 50%~70%）留出输出空间，实测找拐点。
2. 把触发条件从"固定轮数"改成"上下文 token 数达到 L"。
3. 只有当压缩比 `L/s` 足够大（比如 > 2~3）时才压，否则压了也不划算。
4. 评估指标别只看 token 成本，还要看质量衰减和延迟——大 `L` 往往省了压缩钱、赔了长上下文性能。

一句话：调大 `maxlen` 本质是在"频繁压缩"和"不压缩"之间滑动，它能缓解你上一条指出的双调用亏损，但会推高单次回答的上下文成本，因此是个**有最优点**的旋钮，而不是越大越好。
